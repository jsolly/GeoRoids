# Persistent world operations

GeoRoids has one cooperative world with a 60,000-unit radius. It survives empty sessions and server restarts during the current UTC calendar month. Changing `WORLD.generation` or rolling into a new UTC month (`YYYY-MM`) resets saved progress on the next server start or simulation tick so a new expedition can begin.

## Active regions

The server generates deterministic ore deposits in 2,000-unit sectors. It activates sectors around connected pilots and pauses distant sectors. Each client receives nearby asteroid, loot, and projectile rows, plus the shared crew roster, exploration changes, and completed-sector walls. Returning to a harvested sector does not replenish its resources. A visited, fully mapped, empty sector is completed: ships die on its walls, lasers bounce and then become ricochets, anyone already inside or still overlapping the new wall is moved just outside along their heading, and new spawns skip it. Saved worlds store a generation number and a UTC score season; a mismatch of either resets the database instead of loading stale progress.

The local radar spans 3,600 units. Its 125-unit survey cells are permanent shared discoveries. Furnaces are fixed landmarks; a furnace appears on radar after the crew reveals its location. Surveyors passively explore farther and can scan a larger area. Scanned cargo records its Surveyor contributors until consumption, giving each the same full furnace reward as the Hauler.

## Database and credentials

`server/world/WorldStore.ts` uses SQLite with WAL and full synchronous transactions. The database stores world seed, start time, generation, UTC score season, completed sectors, shared exploration, visited sector contents, and pilots (public id, last nickname, monthly score, token digest, and an optional recent flight). A recent flight includes last-seen time, kit, pose, lives, mass, and health. Ordinary flight and partial mining checkpoint every five seconds; terminal asteroid breaks, deliveries, score-bearing loot collections, successful loot blasts, new pilot credentials, and the final player's departure checkpoint immediately. Graceful shutdown checkpoints before closing the database. A hard crash can lose the uncheckpointed ordinary flight or partial-mining interval (normally about five seconds); a committed break or delivery consumes its world object and records its contributor scores in the same transaction.

A private random bearer token identifies a browser's current score. The browser stores it locally; the database stores its SHA-256 digest. A valid token restores that score after a reload, a return to the title screen, or a server restart while the ship still has lives. A live reconnect while the ship is still alive keeps the current pose. After the live socket is gone, Enter Game returns you to that ship only if you come back within 30 seconds of last being seen and still have lives. A longer gap or a missing `lastSeenAt` (including legacy placement rows) starts a new flight with the nickname and kit from the title screen, three lives, full health, and the score you still have. Losing the final life zeros that score. Offline Surveyors receive delivery credit on their next return unless that run already ended. Clearing browser storage loses that credential. Names and public pilot IDs do not grant access to saved score. Treat the database and browser credentials as private. Legacy pilot rows that still contain placement without `lastSeenAt` are loaded as score-only records.

Asteroid impacts remove health, and deaths consume lives. Losing the final life ends that flight and resets the score to 0. Enter Game then starts a new flight with three lives; shared discoveries and the harvested world remain until the UTC calendar month ends. At month rollover the server zeros scores and resets the shared world (exploration, completed sectors, and deposits). Saved worlds also store a UTC score season (`YYYY-MM`); a missing or mismatched season resets the database the same way a generation mismatch does.

The full-screen universe map shows shared exploration and revealed landmarks across the world. Detailed asteroid geometry stays near each pilot. Furnaces and exploration survive restarts. Dropped loot and satellite pickups remain transient session objects, so their map markers expire when those objects disappear or the server restarts.

Local development writes `.data/world.sqlite` by default. This directory and its journals are ignored by Git. `GEOROIDS_WORLD_PATH` overrides the location. The integration runner uses `:memory:` so tests cannot reset a developer's saved world. Direct server instances in tests are in-memory unless given a `worldPath`.

## Railway deployment and recovery

Production requires `GEOROIDS_WORLD_PATH=/data/world.sqlite` and the `world-data` volume mounted at `/data`. The tracked Railway definition prepares a 1 GB volume in `iad` and one server replica. Before opening the database, `server.ts` requires Railway's `RAILWAY_VOLUME_MOUNT_PATH` and checks that the absolute database path belongs directly in that directory. It rejects a missing mount, a different directory, or an in-memory database. Review and apply the volume/path plan before the first server deployment. This change does not apply infrastructure or deploy either service by itself.

Keep the database and its `-wal` and `-shm` files on that mounted volume. Enable daily and weekly volume backups in Railway and verify their live schedule after attaching the volume. For a manual copy, stop the service cleanly first or use SQLite's backup API; copying only the live database file can omit committed WAL transactions. Restore to the same path before starting the server. Invalid saved data stops startup instead of regenerating progress silently. A checkpoint failure blocks new gameplay, makes `/health` return 503, and reaches the fatal shutdown path on the next simulation tick, even when the world is paused. Shutdown closes resources without retrying the unacknowledged world mutation; the restart loads the last committed state.

Do not run multiple server replicas against the same world. The game loop has one authoritative writer; changing replica count requires a different world ownership design.
