# Persistent world operations

GeoRoids has one cooperative world with a 60,000-unit radius. It survives empty sessions and server restarts during the current UTC calendar month. Changing `WORLD.generation` or rolling into a new UTC month (`YYYY-MM`) resets saved progress on the next server start or simulation tick so a new expedition can begin.

## Active regions

The server generates deterministic ore deposits in 2,000-unit sectors. It activates sectors around connected pilots and pauses distant sectors. Each client receives nearby asteroid, loot, and projectile rows, plus the shared crew roster, exploration changes, and completed-sector walls. Returning to a harvested sector does not replenish its resources. A visited, fully mapped, empty sector is completed: ships die on its walls, lasers bounce and then become ricochets, anyone already inside or still overlapping the new wall is moved just outside along their heading, and new spawns skip it. Saved worlds store a generation number and a UTC score season; a mismatch of either resets the database instead of loading stale progress.

The local radar spans 3,600 units. Its 125-unit survey cells are permanent shared discoveries. Sectors holding furnace sites stay open. Fixed furnaces and player-built furnaces appear on radar after the crew reveals their locations. Each Surveyor can build up to three sites per persistent pilot identity. Built furnaces survive death, reconnects, and server restarts; a world or monthly reset clears them. Surveyors passively explore farther and can scan a larger area. Scanned cargo records its Surveyor contributors until consumption, giving each the same full furnace reward as the Hauler.

## Database and credentials

Asteroid density version 2 expands fresh sectors from 24 to 72 deposit slots,
with 14 stationary and 58 drifting rocks per fresh interior sector. On startup, an older saved
world receives only the new slots 24 through 71 in nonempty, uncompleted saved
sectors. Existing rocks retain their positions, velocities, damage, and IDs;
missing legacy slots stay missing. Empty saved sectors and completed sectors
receive no additions. The migration checks IDs across all saved sectors so a
rock that moved across a boundary cannot be duplicated. The first persistence
batch commits the changed sectors and density version together. Subsequent
restarts do not replenish mined additions. This migration preserves the world
generation, exploration, and monthly scores.

Asteroid motion version 1 wakes saved stationary native deposits whose slots
now drift. It runs once at startup before the additive density migration and
commits its marker with the changed sectors. Existing moving rocks retain their
momentum; boosted cargo, reflective targets, missing deposits, empty rows, and
completed sectors are preserved. Intact, stationary three-rock reflective groups
are repositioned into compact pinball pockets within their sector; existing
charge, health, and identity are retained. Partial or boosted groups stay as
they were. Fresh moving slots draw seeded speeds from a
broad range weighted toward slow drift. Terrain forces apply only to ships.

`server/world/WorldStore.ts` uses SQLite with WAL and full synchronous transactions, and the game loop never waits on it. The whole saved world is read once at startup and kept in memory; after that the loop only hands write batches to `server/world/WorkerWorldPersistence.ts`, whose worker thread owns the single writable connection (`server/world/worldStoreWorker.ts`). The integration runners' `:memory:` world cannot cross threads, so `openWorldPersistence` commits it inline instead. The database stores world seed, start time, generation, UTC score season, the server release that last wrote the world row, completed sectors, shared exploration, player-built furnaces, visited sector contents, and pilots (public id, last nickname, monthly score, token digest, optional recent flight, and release stamps). A recent flight includes last-seen time, kit, pose, lives, mass, health, and boost charge. Returning to a recent flight stops active boost and applies the elapsed refill time without granting a fresh tank. Each pilot row records which client and server releases issued the current resume token, which releases last wrote that score, and the server times of those writes. Live score writes also stamp the connected client. Server-only score writes (offline delivery credit and UTC month rollover) stamp the current server release and omit a client release so later migration can tell a browser was not present. Persistence is write-behind: once a second while the world is running, everything that changed since the last flush (moved or mined deposits, scores, credentials, exploration, completed sectors, built furnaces) leaves the loop as one batch and is committed in one transaction, so a batch is never half-applied. The final player's departure, the monthly season rollover, and graceful shutdown flush at once; shutdown waits for the last commit before the process exits, within a fixed budget inside Railway's ten-second SIGTERM window (1.5 s for an in-flight commit to finish, 3.5 s for the worker to commit and close). A writer that cannot keep that budget forfeits the final flush; the skipped flush is logged, and if the writer thread never releases the database (a thread inside a native SQLite call cannot be interrupted, and a normal exit would wait for it) the process ends itself with SIGKILL once the logs are flushed, so a hung disk can never hold a restart hostage. A hard crash therefore loses at most about the last second of play, including a terminal break, delivery, or loot pickup that had not been flushed yet; on restart the world resumes from the last committed batch and the clients rebase to it.

Older world rows without `builtFurnaces` load with no player-built sites. Invalid saved structures fail startup rather than silently dropping them. Construction changes memory only; the existing worker checkpoint writes the world row. A spatial index bounds local intake, spider-safety, and guidance lookups instead of scanning every saved structure.

A private random bearer token identifies a browser's current score. The browser stores it locally with the release identities from the joined acknowledgment; the database stores its SHA-256 digest plus those release stamps and write times. Join sends the client's Git SHA (`clientReleaseId`) and `joined` echoes the stored credential and score releases and their write times. Mismatched releases are recorded for a later migration; they do not block snapshot v1 play. Equal client and server SHAs are not treated as a compatibility check. Legacy rows without stamps still load. A valid token restores that score after a reload, a return to the title screen, or a server restart while the ship still has lives. A live reconnect while the ship is still alive keeps the current pose. After the live socket is gone, Enter Game returns you to that ship only if you come back within 30 seconds of last being seen and still have lives. A longer gap or a missing `lastSeenAt` (including legacy placement rows) starts a new flight with the nickname and kit from the title screen, three lives, full health, and the score you still have. Losing the final life zeros that score. Offline Surveyors receive delivery credit on their next return unless that run already ended. Clearing browser storage loses that credential. Names and public pilot IDs do not grant access to saved score. Treat the database and browser credentials as private. Legacy pilot rows that still contain placement without `lastSeenAt` are loaded as score-only records.

Asteroid impacts remove health, and deaths consume lives. Losing the final life ends that flight and resets the score to 0. Enter Game then starts a new flight with three lives; shared discoveries and the harvested world remain until the UTC calendar month ends. At month rollover the server zeros scores and resets the shared world (exploration, completed sectors, and deposits). Saved worlds also store a UTC score season (`YYYY-MM`); a missing or mismatched season resets the database the same way a generation mismatch does.

The full-screen universe map shows shared exploration and revealed landmarks across the world. Detailed asteroid geometry stays near each pilot. Furnaces and exploration survive restarts. Dropped loot and satellite pickups remain transient session objects, so their map markers expire when those objects disappear or the server restarts.

Asteroid boost couplings are stored with their deposit. Ignited couplings retain their original owner and resume guidance to the nearest furnace after restart, including inside completed sectors. Their sectors stay awake until delivery. Guidance pauses when the world has no players. Legacy saved finite burns had no owner ID; the storage loader cancels only that propulsion, preserving the deposit and its momentum. New snapshots require an owner ID for ignited cargo, so deploy the server and client together and refresh older clients. Armed couplings lose their owner when the live attachment ends and clear before the next motion step; disconnect and removal clear them immediately.

Local development writes `.data/world.sqlite` by default. This directory and its journals are ignored by Git. `GEOROIDS_WORLD_PATH` overrides the location. The integration runner uses `:memory:` so tests cannot reset a developer's saved world. Direct server instances in tests are in-memory unless given a `worldPath`.

## Railway deployment and recovery

Production requires `GEOROIDS_WORLD_PATH=/data/world.sqlite` and the `world-data` volume mounted at `/data`. The tracked Railway definition prepares a 1 GB volume in `iad` and one server replica. Before opening the database, `server.ts` requires Railway's `RAILWAY_VOLUME_MOUNT_PATH` and checks that the absolute database path belongs directly in that directory. It rejects a missing mount, a different directory, or an in-memory database. Review and apply the volume/path plan before the first server deployment. This change does not apply infrastructure or deploy either service by itself.

Keep the database and its `-wal` and `-shm` files on that mounted volume. Enable daily and weekly volume backups in Railway and verify their live schedule after attaching the volume. For a manual copy, stop the service cleanly first or use SQLite's backup API; copying only the live database file can omit committed WAL transactions. Restore to the same path before starting the server. Invalid saved data stops startup instead of regenerating progress silently. A failed commit, reported back from the worker, blocks new gameplay, makes `/health` return 503, and reaches the fatal shutdown path on the next simulation tick, even when the world is paused. Shutdown closes resources without retrying the unacknowledged world mutation; the restart loads the last committed state. `/health` also reports `world.loop` (discarded simulation debt, longest stall, stall count) and `world.persistence` (pending and committed batches, last commit time); a clock step blocked for 250 ms or more logs `game_loop_stalled`.

Do not run multiple server replicas against the same world. The game loop has one authoritative writer; changing replica count requires a different world ownership design.
